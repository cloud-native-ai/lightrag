# Project Instructions for AI Agents

## Project Overview
LightRAG is a lightweight, graph-based Retrieval-Augmented Generation (RAG) framework — a Python library (`lightrag-hku` on PyPI) with a built-in FastAPI REST server. It builds knowledge graphs from documents, supports 10+ storage backends, and provides multiple query modes (local/global/hybrid/naive/mix). The project is dual-delivery: a **Python library** for programmatic use and an **API server** with a React-based WebUI.

## Architecture

### Package Structure (`lightrag/`)
```
lightrag/
├── lightrag.py          # Core LightRAG class (main entry point)
├── operate.py           # Query execution (local/global/hybrid/naive/mix modes)
├── pipeline.py          # Document ingestion pipeline (parse → chunk → extract → index)
├── prompt.py            # LLM prompt templates for extraction & query
├── rerank.py            # Reranker integration
├── base.py              # Base classes and protocols
├── types.py             # Shared type definitions
├── utils.py / utils_graph.py / utils_pipeline.py  # Utility functions
├── api/                 # FastAPI REST server
│   ├── lightrag_server.py   # Server entry point
│   ├── auth.py              # JWT authentication
│   ├── routers/             # document_routes, query_routes, graph_routes, ollama_api
│   └── static/              # WebUI build output served as static files
├── kg/                  # Knowledge graph storage backends
│   ├── shared_storage.py    # Common storage interface (base class)
│   ├── postgres_impl.py     # PostgreSQL + pgvector
│   ├── neo4j_impl.py        # Neo4j graph database
│   ├── milvus_impl.py       # Milvus vector database
│   ├── mongo_impl.py        # MongoDB
│   ├── qdrant_impl.py       # Qdrant vector database
│   ├── redis_impl.py        # Redis
│   ├── opensearch_impl.py   # OpenSearch
│   ├── faiss_impl.py        # FAISS (in-process)
│   ├── networkx_impl.py     # NetworkX (in-memory)
│   └── nano_vector_db_impl.py  # NanoVectorDB (lightweight)
├── llm/                 # LLM provider implementations
│   ├── openai.py, anthropic.py, gemini.py, ollama.py, ...
│   └── binding_options.py   # Role-to-model binding
├── parser/              # Document parsers (native + external)
│   ├── registry.py          # Plugin registry for parser registration
│   ├── routing.py           # Parser dispatch by content type
│   └── markdown/, docx/, external/  # Format-specific parsers
├── chunker/             # Text chunking strategies
├── evaluation/          # RAGAS evaluation & offline retrieval checks
├── sidecar/             # Sidecar format for enriched document processing
├── tools/               # CLI admin tools (hash-password, clean-cache, rebuild-vdb, etc.)
└── _version.py          # Single-source version (dynamic in pyproject.toml)
```

### Data Flow
1. **Ingestion**: Document → Parser → Chunker → LLM Extraction → KG Storage → Vector Index
2. **Query**: User Query → Query Mode (local/global/hybrid/naive/mix) → KG Retrieval + Vector Search → Reranker → LLM Generation → Response + Citations

### Key Conventions
- **Async-first**: All storage operations and LLM calls are async (aiohttp, asyncpg, etc.)
- **Storage abstraction**: Every backend implements `shared_storage.py` base class; new backends follow the same interface
- **Plugin registry**: Parsers register via `lightrag/parser/registry.py`; external parsers can be added without modifying core
- **Role-specific LLM**: Four roles (EXTRACT, QUERY, KEYWORDS, VLM) each independently configurable
- **Deprecated code**: Moved to `deprecated/` subdirectories within `llm/` and `kg/` rather than deleted
- **Environment config**: All configuration via `.env` file; `env.example` is the reference

## Project-Specific Conventions

### Code Patterns
- **Import style**: Absolute imports within `lightrag/` package (e.g., `from lightrag.kg.shared_storage import ...`)
- **Error handling**: Custom exceptions in `lightrag/exceptions.py`; prefer `create_prefixed_exception()` for namespaced errors
- **Logging**: Use `lightrag.utils.logger` or standard `logging.getLogger(__name__)`
- **File operations**: Use `lightrag.file_atomic` for atomic file writes

### Testing Patterns
- Tests mirror source structure: `tests/kg/` ↔ `lightrag/kg/`, `tests/llm/` ↔ `lightrag/llm/`
- `conftest.py` at `tests/` root provides shared fixtures
- `tests/workspace/` for test data and temporary files
- Integration tests for storage backends are in `tests/kg/`

### Common Pitfalls
- **Embedding dimension lock**: Once chosen, embedding model cannot be changed without rebuilding storage
- **Storage backend coupling**: Some backends require dimension defined at table creation (PostgreSQL)
- **Frontend build**: WebUI must be rebuilt after frontend changes (`cd lightrag_webui && bun run build`)
- **uv sync**: Always run `uv sync` after pulling to get updated dependencies
- **.env required**: Server won't start without valid `.env`; use `make env-base` or copy `env.example`
