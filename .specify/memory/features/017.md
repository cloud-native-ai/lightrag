# Feature Detail: API Versioning & Deprecation Policy

**Feature ID**: 017
**Name**: API Versioning & Deprecation Policy
**Description**: Formal API versioning strategy for both library and REST interfaces, with documented deprecation timelines and migration guides.
**Status**: Draft
**Created**: 2026-06-23
**Last Updated**: 2026-06-23

## Overview

LightRAG exposes both a Python library API and a REST API, but lacks a formal versioning strategy for either interface. While the package follows semantic versioning, there is no documented deprecation policy, breaking change timeline, or migration guide template. This is critical for a library that is integrated into downstream applications.

## Latest Review

Initial draft — gap identified during DFX analysis (DFC: Design for Compatibility).

## Key Changes

1. Define REST API versioning strategy (URL path vs header-based)
2. Document deprecation policy: announce → deprecation warning → removal timeline
3. Create migration guide template for breaking changes between major versions
4. Add `DeprecationWarning` infrastructure in the library codebase
5. Version compatibility matrix in documentation

## Implementation Notes

- Python `warnings.warn("...", DeprecationWarning)` for library deprecations
- REST API: consider `/api/v1/` prefix or custom header
- Minimum 1 minor version deprecation period before removal
- Migration guides should be per-major-version
- Compatibility matrix should list Python version, backend versions, and key dependencies

## Future Evolution Suggestions

- OpenAPI spec versioning and changelog
- API compatibility testing across versions
- Long-term support (LTS) release channel
