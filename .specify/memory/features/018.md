# Feature Detail: Structured Logging & Metrics

**Feature ID**: 018
**Name**: Structured Logging & Metrics
**Description**: Standardized structured logging format across all modules, with Prometheus-compatible metrics export for ingestion throughput, query latency, and error rates.
**Status**: Draft
**Created**: 2026-06-23
**Last Updated**: 2026-06-23

## Overview

LightRAG uses standard Python logging but lacks a consistent structured logging format. While Langfuse provides tracing, there is no metrics export for operational monitoring (ingestion rate, query latency, error counts, storage operation timing). Structured logging and metrics would improve production debuggability and enable monitoring dashboards.

## Latest Review

Initial draft — gap identified during DFX analysis (DFO: Design for Observability).

## Key Changes

1. Adopt structured logging format (JSON) with consistent field names across all modules
2. Add request-ID propagation through the ingestion and query pipelines
3. Instrument key operations with Prometheus metrics (counter, histogram, gauge)
4. Expose `/metrics` endpoint on the API server for Prometheus scraping
5. Add health check endpoint (`/health`) with dependency status

## Implementation Notes

- Use `structlog` or `python-json-logger` for structured logging
- Prometheus client: `prometheus_client` or `prometheus-fastapi-instrumentator`
- Request-ID: FastAPI middleware or `X-Request-ID` header
- Metrics should cover: `lightrag_ingestion_duration_seconds`, `lightrag_query_duration_seconds`, `lightrag_errors_total`
- Health check should report LLM provider, storage backend, and embedding service status

## Future Evolution Suggestions

- Grafana dashboard templates for LightRAG metrics
- Alerting rules for common failure modes
- Distributed tracing with OpenTelemetry
